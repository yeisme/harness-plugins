## ADDED Requirements

### Requirement: Project automation bindings MUST pin published workflow contracts

Each ProjectAutomationBinding MUST reference a tenant/workspace/project/dataset, schema revision, trigger definition, published WorkflowDefinition ref/version/checksum, typed input mapping, required role/scope, cost/approval policy, automation actor, revision and audit metadata. A binding MUST NOT embed executable steps, arbitrary code, URLs, credentials or Owner payloads.

#### Scenario: A binding references a draft workflow definition
- **WHEN** a user attempts to enable a binding that references an unpublished, deprecated, checksum-mismatched or unsupported WorkflowDefinition
- **THEN** the service MUST return `automation_stale` or `needs_contract`
- **AND** it MUST NOT create a run or copy workflow steps into the binding

### Requirement: Project triggers MUST originate from committed server events or schedules

V1 Project automation triggers MUST be limited to approved `record_created`, `record_changed`, `status_transitioned`, `manual`, `schedule` and `approved_event` forms. Record and status triggers MUST consume committed WorkItem event/outbox records; schedules MUST be generated by the server worker. Browser events and local clocks MUST NOT be accepted as trigger truth.

#### Scenario: The same WorkItem event is delivered twice
- **WHEN** a committed event is redelivered to the trigger worker for the same binding version
- **THEN** `(eventRef, bindingRef, bindingVersion)` deduplication MUST start at most one WorkflowRun
- **AND** the duplicate delivery MUST return or record the existing run ref without repeating downstream mutation

### Requirement: Trigger filters and input mappings MUST be typed and access-trimmed

Trigger filters and input mappings MUST use an allowlisted AST over permitted WorkItem system/custom fields, safe refs and digests. The service MUST validate field kind, schema revision, visibility, size and destination input schema before starting a run. Hidden values, raw description, arbitrary expressions and Owner payloads MUST NOT enter workflow state, logs or evidence.

#### Scenario: A field used by a binding is archived
- **WHEN** an enabled binding references an archived, replaced or newly hidden field
- **THEN** the binding MUST become `stale` and stop starting new runs until explicitly migrated and revalidated
- **AND** existing runs MUST continue only under their pinned definition and already-materialized safe input contract

### Requirement: Automation enablement MUST be explicit, versioned and fail closed

Bindings MUST transition through `draft`, `enabled`, `paused`, `stale`, `needs_contract` and `disabled` using expected revision and idempotency. Enabling MUST revalidate principal, project role, schema, trigger, workflow definition, automation actor, capability, quota, cost and approval policy. Enabling MUST NOT replay historical events by default.

#### Scenario: An Agent proposes an automation
- **WHEN** an Agent creates or edits an automation proposal
- **THEN** the draft MUST enter ProposalAuthority or another approved explicit decision path before enablement
- **AND** Agent output, browser state or a canvas edge MUST NOT directly enable the binding

### Requirement: Automation execution MUST use WorkflowService and TaskService truth

ProjectAutomationService MUST start and observe runs through the durable WorkflowService. Any WorkItem or Owner mutation step MUST execute through the approved step registry, TaskService gates and Owner receipt/reconcile path. ProjectAutomationService MUST NOT implement a second scheduler, worker, retry loop or Owner adapter.

#### Scenario: An Owner mutation has an unknown outcome
- **WHEN** a workflow step cannot determine whether an Owner accepted the mutation
- **THEN** the step and run MUST enter the existing reconciling or `unknown_accept` path and expose the receipt/idempotency safe ref
- **AND** Project automation MUST NOT submit a replacement mutation or mark the related WorkItem complete

### Requirement: Automation authority MUST be revalidated at trigger and dispatch time

The system MUST validate R1 membership, ProjectRolePolicy, automation actor delegation, field visibility, capability, cost and approval at binding enablement, each trigger, and each side-effecting workflow step. Revocation MUST stop new runs and new dispatch while already-sent mutations continue receipt/reconcile.

#### Scenario: Automation actor delegation is revoked
- **WHEN** the automation actor or project policy is revoked after a binding was enabled
- **THEN** the binding MUST become paused, stale or `permission_required`, and no new run or dispatch may begin
- **AND** already-dispatched attempts MUST remain observable and reconcile under their original idempotency keys

### Requirement: Automation pause, disable and recovery MUST preserve run truth

Pausing or disabling a binding MUST stop new trigger acceptance after a documented fence and MUST NOT cancel or rewrite existing WorkflowRuns. Run pause/resume/cancel/reconcile and operator intervention MUST use WorkflowService controls and audit semantics.

#### Scenario: A binding is disabled during event backlog
- **WHEN** an administrator disables a binding while unprocessed events remain
- **THEN** the trigger worker MUST record the disable fence and must not start runs for events beyond the allowed fence
- **AND** events and existing runs MUST remain auditable without being silently discarded, replayed or rewritten as cancelled

### Requirement: Manual automation MUST use the same action and proposal boundaries

Manual run from a record, selection, Inspector, Command Palette or Agent suggestion MUST resolve one server-authored action descriptor containing binding version, workflow definition version, input digest, permission, confirmation, cost, idempotency and recovery. All entry points MUST create the same WorkflowRun semantics.

#### Scenario: A user runs automation from a Kanban selection
- **WHEN** the user selects records and invokes an approved manual automation
- **THEN** the system MUST validate selection size, record versions, field visibility, binding and workflow contracts before creating the run
- **AND** a stale, unauthorized or oversized selection MUST fail without partial hidden input or a browser-side fallback run

### Requirement: Automation events, logs and evidence MUST be correlated and redacted

Binding, trigger, run, step, Task, receipt and recovery records MUST share safe correlation refs and structured audit events. Logs and evidence MUST include timing, state, version, error and redaction metadata while excluding cell contents, credentials, Owner payloads, raw prompts and private paths.

#### Scenario: An automation integration test fails
- **WHEN** an integration, system or e2e automation test exits with failure
- **THEN** the evidence runner MUST still write `summary.json`, command, stdout, stderr, env and artifacts under `temp/integration-test-runs/<run-id>/`
- **AND** persisted evidence MUST be redacted and identify the failing binding/run/step through safe refs only

### Requirement: Project automation contracts MUST keep four-transport parity

Binding CRUD, validate, enable, pause, disable, manual start, list runs, watch events and recovery operations MUST expose the same version, idempotency, state, error, cursor, receipt and redaction semantics through HTTP, gRPC, JSON-RPC and TypeScript SDK, and MUST enter the canonical services.

#### Scenario: Automation parity and restart test
- **WHEN** the conformance suite enables a binding, delivers a duplicate trigger, starts a run, restarts the trigger worker and resumes observation through all transports
- **THEN** the same binding/run refs, dedupe outcome, state versions and events MUST be observed
- **AND** no transport or restart path may bypass WorkflowService, TaskService, authority or reconcile

### Requirement: Project automation MUST meet fault, quota and promotion gates

Before Owner mutation automation is promoted, the system MUST pass duplicate-event, trigger storm, worker crash, database outage, permission revoke, approval stale, Owner 429/5xx/offline, `unknown_accept`, kill switch, rollback and soak scenarios using an approved test tenant and real receipt/status/reconcile contract.

#### Scenario: Automation canary promotion is evaluated
- **WHEN** the project automation canary runs against a real approved Owner operation
- **THEN** no duplicate mutation, false completion or hidden unknown outcome may occur, and quota/lag/readiness/rollback evidence MUST satisfy the approved budget
- **AND** fixture-only, browser-only or manual-observation evidence MUST NOT promote the capability
